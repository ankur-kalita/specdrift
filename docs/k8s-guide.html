Overview

What we built, and why each piece exists

Four tools, stacked. Each one solves a problem created by the one before it.

ToolThe problem it solves
Docker"It works on my machine." Packs specdrift plus its whole environment into one image that runs identically anywhere.
kindYou need a Kubernetes cluster to practise on, and you don't have a datacentre. kind builds one out of Docker containers on your laptop.
HelmKubernetes YAML is repetitive and environment-specific. Helm turns it into a template with swappable values.
Argo CDSomeone has to actually run kubectl apply. Argo CD watches your git repo and applies changes for you, forever.

Two separate paths into the cluster: the chart travels through git and Argo CD; the image is pushed straight onto the nodes. Forgetting the second one is the most common way this setup fails.

Part 1

Docker: putting specdrift in a box

Kubernetes can't run a Rust binary. It only runs container images. So step one is turning specdrift into one.

The Dockerfile, stage by stage

The key idea is a multi-stage build. Compiling Rust needs a ~1.5 GB toolchain. Running the result needs a 5 MB binary. A multi-stage build uses the big thing, then throws it away.

Dockerfile
# ---- Stage 1: build ----
FROM rust:1-slim AS builder
WORKDIR /src
COPY Cargo.toml Cargo.lock ./
COPY src ./src
RUN cargo build --release --locked

# ---- Stage 2: run ----
FROM debian:stable-slim
RUN useradd --create-home --shell /bin/bash drift
COPY --from=builder /src/target/release/specdrift /usr/local/bin/specdrift
USER drift
WORKDIR /home/drift
ENTRYPOINT ["/usr/local/bin/specdrift"]
CMD ["--help"]

Line by line, the parts that matter:

LineWhy
AS builderNames this stage so the second one can steal files from it.
--lockedForces the exact dependency versions from Cargo.lock. Without it a build could silently pick newer libraries than you tested with.
COPY --from=builderThe whole trick. Copies just the compiled binary out of stage 1. Stage 1 is then discarded.
useradd + USER driftRuns as a normal user, not root. Kubernetes security policies reject root containers, and specdrift only reads system info — it needs no privileges at all.
ENTRYPOINTThe command that always runs. Anything you pass becomes its arguments, so docker run specdrift snapshot works naturally.

.dockerignore

Same idea as .gitignore — it stops files being sent to the build. Critically it excludes target/, which is hundreds of megabytes of build output that would be copied in and then recompiled anyway.

.dockerignore
target/
tests/
docs/
.github/
.git/
*.json

Building it

zsh
$ docker build -t specdrift:0.1.0 -t specdrift:latest .
...
naming to docker.io/library/specdrift:0.1.0 done

$ docker images specdrift
specdrift:0.1.0  142MB
specdrift:latest 142MB

Two tags, one image. 0.1.0 is the one to reference in Kubernetes — latest is a trap in clusters, because it gives you no way to know what's actually deployed.

What the container thinks the machine is

This is the genuinely interesting bit, and it matters for a tool whose job is spotting hardware change:

FactValueWhose machine is that?
os.nameDebian GNU/Linuxthe container's userspace
os.kernel7.0.12-linuxkitthe Docker VM's kernel
cpu.count10the VM's CPU allocation
memory.total10.4 GBthe VM's RAM, not your 17 GB
Why this is worth knowing

Your Mac appears nowhere in that list. A container reports a blend of three different machines. So "what does this container think it's running on" is a real question with a surprising answer — and a drift detector is exactly the right tool for asking it.

Part 2

kind: a cluster on your laptop

kind stands for Kubernetes IN Docker. Each "node" of the cluster is a Docker container running kubelet. It is not a simulation — it's real Kubernetes, just with containers standing in for machines.

The cluster config

k8s/kind-cluster.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: specdrift

nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30080
        hostPort: 30080
        protocol: TCP
  - role: worker
  - role: worker
  • 1 control-plane + 2 workers. Three nodes, because for a drift detector comparing nodes against each other is the interesting experiment. A single-node cluster can't show you that.
  • extraPortMappings punches a hole from your Mac into the cluster on port 30080, so a NodePort Service could be reached later without port-forwarding.

Creating it

zsh
$ kind create cluster --config k8s/kind-cluster.yaml --wait 120s
 ✓ Installing CNI
 ✓ Installing StorageClass
 ✓ Joining worker nodes
 ✓ Waiting ≤ 2m0s for control-plane = Ready
 ✓ Ready after 11s
Set kubectl context to "kind-specdrift"
zsh
$ kubectl get nodes
NAME                      STATUS   ROLES           VERSION
specdrift-control-plane   Ready    control-plane   v1.37.0
specdrift-worker          Ready    <none>          v1.37.0
specdrift-worker2         Ready    <none>          v1.37.0

Contexts — which cluster am I talking to?

A context is the cluster kubectl currently points at. You now have three, and mixing them up is the easiest way to break something you didn't mean to touch:

zsh
$ kubectl config get-contexts
CURRENT   NAME
          docker-desktop     ← Docker Desktop's own cluster
          kind-microshop     ← your class project
*         kind-specdrift     ← this one
Check before you apply

kubectl config current-context before anything destructive. kind create cluster switches your context automatically — so your terminal silently started pointing somewhere new. Your class cluster kind-microshop was never touched, but only because we checked.

Switch with: kubectl config use-context kind-microshop

Getting the image into the cluster — the big gotcha

The cluster nodes are separate containers. They have their own image storage and cannot see images on your Mac's Docker. An image that builds fine locally will fail in the cluster with ImagePullBackOff — Kubernetes goes looking for it in a registry, and it isn't there.

Normally you'd push to a registry (Docker Hub, GHCR). kind offers a shortcut:

zsh
$ kind load docker-image specdrift:0.1.0 --name specdrift
Image: "specdrift:0.1.0" ... not yet present on node "specdrift-worker", loading...
Image: "specdrift:0.1.0" ... not yet present on node "specdrift-worker2", loading...
Image: "specdrift:0.1.0" ... not yet present on node "specdrift-control-plane", loading...

$ # verify on each node
specdrift-control-plane    1
specdrift-worker           1
specdrift-worker2          1
The consequence for your YAML

Because the image exists only on the nodes and in no registry, imagePullPolicy must be IfNotPresent or Never. The default for a :latest tag is Always — which would ignore the local copy, try to pull, and fail. This is why the chart sets it explicitly, and why the Argo CD Application pins it again as a parameter.

You must re-run kind load every time you rebuild the image. Argo CD syncs the chart from git; it has no idea your image changed.

Part 3

Argo CD: the GitOps robot

What GitOps actually means

Up to now, deploying meant you typing kubectl apply. That has two problems: nobody knows what's actually running, and anyone can change the cluster by hand and never tell you.

GitOps inverts it. Your git repo is the single source of truth for what should be running. A robot in the cluster continuously compares reality against git and fixes any difference.

The mental model

CI (which you built earlier) answers "is this code good?" — it pushes. Argo CD answers "does the cluster match git?" — it pulls. They're two halves of the same pipeline, and they never talk to each other directly. Git is the handoff.

Installing it

zsh
$ kubectl create namespace argocd
$ kubectl apply -n argocd --server-side --force-conflicts \
    -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

Note --server-side --force-conflicts. This is not optional, and here is why.

The error you get without it 
The CustomResourceDefinition "applicationsets.argoproj.io"
is invalid: metadata.annotations: Too long:
may not be more than 262144 bytes

Plain kubectl apply saves a copy of the entire resource into an annotation called last-applied-configuration, so it can work out what changed next time. Argo CD's applicationsets CRD is bigger than the 256 KB annotation limit, so that copy won't fit.

Server-side apply lets the API server track changes itself, so no annotation is needed. Your instructor's command uses the same two flags — this is simply how Argo CD has to be installed.

A first attempt without the flags left the cluster half-installed: the CRD was missing. Re-running with them fixed it, and all three CRDs appeared:

zsh
$ kubectl get crd | grep argoproj
applications.argoproj.io       Namespaced   v1alpha1
applicationsets.argoproj.io    Namespaced   v1alpha1
appprojects.argoproj.io        Namespaced   v1alpha1

The pod that looks broken but isn't

During startup argocd-server sits at 0/1, and if you describe it you see:

zsh
Warning  Failed  13s  kubelet  Error: secret "argocd-redis" not found

That secret is generated by Redis's own init job, which hasn't finished yet. It resolves on its own in 30–60 seconds. All 7 pods then go 1/1:

zsh
$ kubectl get pods -n argocd
argocd-application-controller-0        1/1  Running
argocd-applicationset-controller-...   1/1  Running
argocd-dex-server-...                  1/1  Running
argocd-notifications-controller-...    1/1  Running
argocd-redis-...                       1/1  Running
argocd-repo-server-...                 1/1  Running
argocd-server-...                      1/1  Running

Opening the UI

Argo CD isn't exposed outside the cluster by default. port-forward tunnels it to your Mac:

zsh
$ kubectl port-forward svc/argocd-server -n argocd 8081:443
# then open https://localhost:8081
# the browser will warn about the certificate — it's self-signed. Proceed.

$ # username: admin — get the password with:
$ kubectl -n argocd get secret argocd-initial-admin-secret \
    -o jsonpath="{.data.password}" | base64 -d
Why the password isn't written down here

This file lives in a public GitHub repo. Secrets never go in committed files — always fetch them with the command above. The habit matters more than this one throwaway password does.

Port 8080 is already taken — use 8081

The first attempt used 8080 and the browser couldn't load the page, even though port-forward had started and printed Forwarding from 127.0.0.1:8080. The log then filled with:

error creating error stream for port 8080 -> 8080: Timeout occurred

Docker Desktop was already listening on 8080. Two processes cannot own the same port, so the tunnel opened but every request timed out — which from the browser is indistinguishable from "nothing is running".

$ lsof -nP -iTCP:8080 -sTCP:LISTEN
com.docke  46004  TCP *:8080 (LISTEN)      ← Docker got there first
kubectl    59818  TCP 127.0.0.1:8080       ← ours, losing

The diagnostic: if a port-forward starts cleanly but the browser can't connect, run that lsof on the port. Anything listed means pick a different number — any free port in 8000–9000 works, the value is arbitrary.

Part 4

Helm: the chart

Raw Kubernetes YAML has no variables. Deploying the same app to dev and prod means two near-identical files that drift apart. Helm is templating for Kubernetes: one set of templates, plus a values file per environment.

What's in the chart

charts/specdrift/
Chart.yaml              name, version, description
values.yaml             default values — every knob, documented
values-dev.yaml         dev overrides (fast schedule, verbose)
values-prod.yaml        prod overrides (DaemonSet, hourly)
.helmignore             files to keep out of the packaged chart
templates/
  _helpers.tpl          reusable snippets (names, labels)
  serviceaccount.yaml   the identity pods run as
  configmap-baseline.yaml  holds the baseline snapshot for diff mode
  cronjob.yaml          workload=cronjob
  daemonset.yaml        workload=daemonset
  NOTES.txt             printed after install — what to do next

The two decisions the chart exposes

ValueOptionsMeaning
workloadcronjob / daemonsetCronJob: runs on a schedule, one pod per run, exits. DaemonSet: one long-lived pod on every node, looping — so you can compare nodes.
modesnapshot / diffsnapshot: record facts and print them. diff: compare against a stored baseline and exit 1 if drifted.

Three details in the templates worth understanding

1. readOnlyRootFilesystem forces a writable volume

The pod's filesystem is read-only for security, so specdrift can't write its snapshot anywhere normal. An emptyDir volume is mounted at /work to give it exactly one writable path. emptyDir lives and dies with the pod — correct here, because the snapshot goes to the logs, not to storage.

2. The pod knows which node it's on

templates/cronjob.yaml — excerpt
env:
  - name: SPECDRIFT_NODE
    valueFrom:
      fieldRef:
        fieldPath: spec.nodeName

A fieldRef injects information about the pod into the pod. Without it, a drift report from a 3-node cluster can't tell you which node drifted — which would make it useless.

3. A guard rail instead of broken YAML

templates/configmap-baseline.yaml — excerpt
{{- if eq .Values.mode "diff" }}
{{- if not .Values.baseline }}
{{- fail "mode=diff requires a baseline. Set .Values.baseline ..." }}
{{- end }}

Setting mode=diff with no baseline is a mistake. Helm's fail stops rendering with a message telling you how to fix it, rather than deploying a pod that crash-loops with a confusing error:

zsh
$ helm template test . --set mode=diff
Error: execution error at (specdrift/templates/configmap-baseline.yaml:3:4):
mode=diff requires a baseline. Set .Values.baseline to a snapshot JSON
string (generate one with: docker run --rm specdrift:0.1.0 snapshot -o /dev/stdout)

Testing the chart without a cluster

helm template renders the YAML and prints it. Nothing is deployed. This is how you check a chart quickly:

zsh
$ helm lint charts/specdrift
1 chart(s) linted, 0 chart(s) failed

$ helm template test charts/specdrift
# default: CronJob, snapshot mode, */5 schedule

$ helm template test charts/specdrift --set workload=daemonset
# DaemonSet instead

$ helm template test charts/specdrift -f values.yaml -f values-dev.yaml
# schedule becomes */2 — the later file wins
Part 5

Tying it together: the Argo CD Application

An Application is a Kubernetes resource that says: take the chart at this git path, render it with these values, and keep this namespace matching the result.

The thing that surprises everyone

Argo CD does not run helm install. It runs helm template to render plain YAML, then manages those resources itself. So helm list shows nothing — Helm isn't tracking a release, Argo CD is. Helm is used purely as a rendering engine.

The manifest

k8s/argocd-application.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: specdrift
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default

  source:
    repoURL: https://github.com/ankur-kalita/specdrift.git
    targetRevision: main
    path: charts/specdrift

    helm:
      releaseName: specdrift

      valueFiles:
        - values.yaml
        - values-dev.yaml
      ignoreMissingValueFiles: true

      valuesObject:
        podLabels:
          managed-by-argocd: "true"

      parameters:
        - name: image.pullPolicy
          value: IfNotPresent

      skipTests: true
      skipCrds: true

  destination:
    server: https://kubernetes.default.svc
    namespace: specdrift

  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
      - ServerSideApply=true

The value precedence ladder

This is the core of the Argo CD Helm guide. Four places can set the same value, and they have a strict pecking order — lowest first:

1 · weakest chart's values.yamlschedule: */5 * * * *
2 valueFilesvalues-dev.yaml → schedule: */2 * * * *
3 values / valuesObjectinline in the Application
4 · wins parametersoverrides everything above it

Within valueFiles, later files beat earlier ones — so the order of that list is meaningful, not cosmetic.

What the other fields do

FieldEffect
finalizersWithout it, deleting the Application orphans everything it created — the pods keep running with nothing managing them.
targetRevision: mainWhich git branch or tag to follow. Could be a tag like v0.1.0 to pin a version.
releaseNameDefaults to the Application name. Set explicitly so renaming the Application doesn't rename every resource it owns.
ignoreMissingValueFilesAn absent optional overlay file is skipped instead of failing the whole sync.
prune: trueResources deleted from git get deleted from the cluster. Without it, removed things linger forever.
selfHeal: trueManual kubectl edit changes get reverted to match git. This is GitOps actually being enforced.
CreateNamespace=trueCreates the destination namespace if missing.
ServerSideApply=trueSame annotation-size reason Argo CD's own install needed it.
selfHeal will fight you

With selfHeal: true, editing anything by hand gets silently reverted within minutes. That's the point — but while experimenting it feels like the cluster is haunted. To change something, change git. To experiment by hand, set selfHeal: false first.

Proving it works

The chart had to be pushed to GitHub first — Argo CD reads git, not your laptop:

zsh
$ git add -A && git commit -m "feat: add Docker image, kind cluster, Helm chart, Argo CD app"
$ git push

$ kubectl apply -f k8s/argocd-application.yaml

Checking each layer of the ladder actually applied

Running it now instead of waiting

You don't have to wait for the schedule. --from=cronjob/... creates a one-off Job from the CronJob's template:

zsh
$ kubectl create job --from=cronjob/specdrift drift-now -n specdrift
job.batch/drift-now created

$ kubectl logs -n specdrift -l job-name=drift-now --tail=-1
saved 24 facts to /work/snapshot.json
{
  "version": 1,
  "captured_at": "2026-09-12T11:59:20Z",
  "facts": {
    "cpu.brand": { "value": "", "class": "stable" },
    "cpu.count": { "value": "10", "class": "stable" },
    "disk./.total": { "value": "485473984512", "class": "stable" },
    ...
A real finding: cpu.brand is empty

On your Mac specdrift reports "Apple M4". Inside the cluster it reports "".

On arm64 Linux, /proc/cpuinfo has no model name field — that's an x86 convention. So sysinfo has nothing to read and returns an empty string.

It's not a crash, but it is a gap: an empty "stable" fact would look like drift if a future run ever did populate it. Worth fixing later by either omitting empty facts or falling back to another source.

Part 7

The four experiments

Having built it, we ran it — and the running is where everything was actually learned.

1 — Break GitOps by hand

The CronJob ran every 2 minutes. It was sabotaged directly in the cluster to run once a year, exactly as if someone had “fixed” production by hand:

zsh
$ kubectl patch cronjob specdrift -n specdrift --type merge \
    -p '{"spec":{"schedule":"0 0 1 1 *"}}'
cronjob.batch/specdrift patched

$ # 5 seconds later...
  5s  argocd=Synced   schedule=*/2 * * * *
>>> REVERTED. Argo CD put it back.

Argo CD's own event log tells the whole story inside 27 seconds:

kubectl get events -n argocd
Synced -> OutOfSync                  ← noticed the edit
Initiated automated sync             ← decided to fix it
Partial sync operation succeeded     ← applied git's version
OutOfSync -> Synced                  ← done

The deeper part is who Kubernetes thinks owns that field:

zsh
$ kubectl get cronjob specdrift -n specdrift \
    -o jsonpath='{range .metadata.managedFields[*]}{.manager}{" -> "}{.operation}{"\n"}{end}'
argocd-controller -> Apply
kube-controller-manager -> Update
What this means in practice

Because ServerSideApply=true is set, Kubernetes records who owns which field. Argo CD owns schedule. The manual patch wasn't merely overwritten — it was an unauthorised edit to a field with a registered owner.

In a GitOps cluster, kubectl edit is not a way to change anything. It is a way to waste five seconds. The only way to change the cluster is to change git — so every change carries a commit, an author and a diff.

2 — Change git, get a different cluster

One line in values-dev.yaml: workload: cronjob → daemonset. Commit, push, and nudge Argo CD instead of waiting for its 3-minute poll:

zsh
$ kubectl annotate application specdrift -n argocd \
    argocd.argoproj.io/refresh=hard --overwrite

Two things happened, both instructive.

The CronJob was deleted

Nobody deleted it. It disappeared from git, so prune: true removed it from the cluster. Without that setting it would have lingered forever, still firing every 2 minutes, owned by nothing.

Two pods, not three

A DaemonSet is meant to run on every node. Only the two workers got one:

zsh
$ kubectl get pods -n specdrift -o custom-columns='POD:.metadata.name,NODE:.spec.nodeName'
specdrift-84lnr   specdrift-worker
specdrift-ftglz   specdrift-worker2

$ kubectl get node specdrift-control-plane -o jsonpath='{range .spec.taints[*]}{.key}{"="}{.effect}{"\n"}{end}'
node-role.kubernetes.io/control-plane=NoSchedule

A taint is a “keep out” sign on a node; Kubernetes puts that one there so app workloads don't crowd the node running the cluster's brain. A pod needs a matching toleration to be allowed on. values-dev.yaml has none — values-prod.yaml does, which is precisely why it was written that way.

3 — Comparing the nodes: a negative result

The point of three nodes was to compare them. They came back byte-for-byte identical, including uptime to the second:

Factworkerworker2Reality
cpu.count1010the VM has 10
memory.total10.4 GB10.4 GBthe VM has 10.4 GB
system.uptime_secs17011701the VM's uptime

kind nodes are not machines — they are containers sharing one Linux VM. Each “node” looks at that VM and reports the VM's hardware.

Add it up: 30 CPUs on a 10-CPU machine

This is not a specdrift quirk; it is one of the most expensive real problems in containers. A JVM, a Go runtime or an nginx worker pool sizes itself from cpu.count. Put one in a container limited to half a CPU on a 64-core host and it spawns 64 threads and thrashes. That is why GOMAXPROCS, -XX:ActiveProcessorCount and cgroup-aware runtimes exist.

Two honest conclusions: node-to-node comparison cannot work in kind (there is only one machine underneath), and specdrift has a real gap — it should read cgroup limits (/sys/fs/cgroup/memory.max, cpu.max) to report what the container is allowed, not what the host has. Still open.

4 — A real drift alarm, and the two bugs it exposed

A baseline was captured from inside the cluster (so the comparison is like-for-like, not against a macOS snapshot), embedded in values-dev.yaml, and mode switched to diff. It worked — and immediately reported nonsense:

kubectl logs -n specdrift
  ~ disk./.available                     ...844224 -> ...963008
  + disk./baseline.available             439729963008
  + disk./baseline.total                 485473984512
  ~ disk./dev/termination-log.available  ...844224 -> ...963008
  ~ disk./etc/hostname.available         ...844224 -> ...963008
  ~ disk./etc/hosts.available            ...844224 -> ...963008
  ~ disk./etc/resolv.conf.available      ...844224 -> ...963008
  ~ disk./work.available                 ...844224 -> ...963008
11 changes since 2026-09-12T12:15:22Z

Bug 1 — the tool created the drift it detected

To run diff, the chart mounts the baseline ConfigMap at /baseline. That mount is a filesystem, so it was enumerated as a new disk. The baseline had been captured in snapshot mode, when /baseline did not exist.

Switching on drift detection caused drift. And disk./baseline.total is classified stable, so it fired even without --all — making the feature permanently, uselessly noisy.

Bug 2 — one disk counted seven times

Note the identical numbers on every line above. Those are not six disks. Verified inside the pod:

kubectl exec -- cat /proc/self/mounts
overlay     /                      overlay
/dev/vda1   /work                  ext4
/dev/vda1   /baseline              ext4
/dev/vda1   /etc/hosts             ext4
/dev/vda1   /dev/termination-log   ext4
/dev/vda1   /etc/hostname          ext4
/dev/vda1   /etc/resolv.conf       ext4

One real filesystem, six names for it. Kubernetes bind-mounts /dev/vda1 repeatedly to inject /etc/hosts, the termination log and so on. specdrift counted each as a separate disk, so one change was reported six times.

The fix: key by device, not mount point

Both bugs die to one idea. A device is a filesystem's stable identity; mount points come and go. Six mounts collapse to one entry, and mounting /baseline no longer invents anything.

Crucially the logic is pure, so it went in a new module rather than into collect.rs — which keeps collect.rs dumb and makes the rule unit-testable:

src/disks.rs — the signature
pub struct RawDisk {
    pub device: String,        // "/dev/vda1", "overlay"
    pub mount_point: String,   // "/work"
    pub total: u64,
    pub available: u64,
}

/// One real filesystem. Note: no mount point. A filesystem can be
/// mounted at several paths at once, and which paths those are is
/// not a property of the hardware.
pub struct Filesystem {
    pub device: String,
    pub total: u64,
    pub available: u64,
}

Post-mortem

Everything that broke, in order

  1. Docker daemon not running

    docker ps → "check if the daemon is running". Everything depends on Docker, including kind, because kind nodes are containers. Fixed with open -a Docker and an 8-second wait.

  2. Stale kubeconfig pointing at a dead cluster

    kubectl get nodes against docker-desktop gave connection refused on port 50489. The context existed from an earlier session but the cluster behind it was gone. A context is just saved connection details — it doesn't prove anything is alive.

  3. Argo CD CRD too big for kubectl apply

    metadata.annotations: Too long: may not be more than 262144 bytes. Client-side apply stores the whole resource in an annotation; that CRD exceeds the limit. Fixed with --server-side --force-conflicts. The first partial install had to be re-applied.

  4. argocd-server: secret "argocd-redis" not found

    Looked like a real failure, was just startup ordering — Redis generates that secret from its own init job. Resolved itself in under a minute. Not every red status needs fixing; some need waiting.

  5. cpu.brand empty on arm64 Linux

    A genuine limitation in specdrift, surfaced only by running in the cluster. Same shape as the cpu.frequency_mhz bug CI caught earlier: a different environment revealed an assumption baked in on the Mac.

  6. Port 8080 clash with Docker Desktop

    port-forward reported success, the browser got nothing. Docker Desktop already held 8080, so every request timed out. Moved to 8081. A process starting successfully is not proof it is reachable — check with lsof before blaming the cluster.

The pattern

Four of those five weren't bugs in anything we wrote — they were environment problems: something not running, something stale, a platform limit, a startup race. That is what most real DevOps debugging actually is.

Reference

Glossary

Open whichever ones you need. No order — dip in.

image vs container

An image is the recipe — a frozen filesystem plus a command. A container is one running copy of it. One image, many containers, same way one class makes many objects.

multi-stage build

A Dockerfile with several FROM lines. Earlier stages do heavy work (compiling); the final stage copies out only what's needed. Our builder stage is ~1.5 GB; the image we keep is 142 MB.

registry

A server that stores images — Docker Hub, GitHub Container Registry. Kubernetes normally pulls from one. We skipped it with kind load docker-image, which is why imagePullPolicy has to be IfNotPresent.

node

A machine that runs your workloads. In a real cluster it's a server; in kind it's a Docker container pretending to be one. Ours: one control-plane and two workers.

pod

The smallest thing Kubernetes runs — one or more containers that share a network address and storage. You rarely create pods directly; something else (a CronJob, a DaemonSet) creates them for you.

namespace

A folder inside a cluster, for keeping unrelated things apart. We use two: argocd for the robot, specdrift for our app.

context

Saved details for talking to one cluster — address, credentials, default namespace. kubectl uses whichever is current. A context can exist for a cluster that's long gone, which is exactly what bit us with docker-desktop.

CronJob

Runs a pod on a schedule, cron-style. */2 * * * * means every 2 minutes. Each run creates a fresh pod that does its work and exits.

DaemonSet

Runs exactly one pod on every node, automatically — including nodes added later. Normally used for log collectors and monitoring agents. Here it lets specdrift compare nodes against each other.

emptyDir

Scratch storage that's created empty when a pod starts and deleted when it stops. We need it because the container's root filesystem is read-only, and specdrift has to write its snapshot somewhere.

ConfigMap

A blob of configuration stored in the cluster, mountable as files in a pod. We use one to hold the baseline snapshot for diff mode. (For passwords you'd use a Secret instead.)

CRD (CustomResourceDefinition)

Teaches Kubernetes a new kind of object. Argo CD installs three, which is how kind: Application becomes a thing the cluster understands. The big one is what blew past the annotation size limit.

server-side apply

The API server tracks who owns which fields, instead of kubectl stashing a full copy of the resource in an annotation. Needed for resources too big for that 256 KB annotation — like Argo CD's CRDs.

GitOps

Git is the source of truth for what should be running; a robot in the cluster continuously makes reality match. Nobody deploys by hand, and every change has a commit behind it.

sync / drift (Argo CD sense)

Synced = cluster matches git. OutOfSync = it doesn't, either because git changed or someone edited the cluster. With selfHeal: true, Argo CD fixes the second case automatically. (Different sense of "drift" from specdrift's — one is config, one is hardware.)

Helm chart / release / values

A chart is the template package. Values fill in the blanks. A release is one installed instance. Note: with Argo CD there's no real Helm release — Argo CD only borrows Helm to render YAML.

port-forward

Tunnels a port on your laptop to a service inside the cluster. Perfect for poking at something during development; not how you'd expose anything for real (that's Services and Ingress).

ImagePullBackOff

Kubernetes couldn't fetch the image and is retrying with growing delays. Nearly always a typo in the name/tag, a missing registry login, or — the case here — an image that only exists on your laptop and was never loaded into the cluster.

When you're done

Cleanup

Ordered from gentlest to most complete. Note that step 1 alone won't do much while selfHeal is on — Argo CD just puts things back.

stop the app, keep the cluster
kubectl delete -f k8s/argocd-application.yaml
# the finalizer makes this delete the CronJob and friends too
delete the whole cluster
kind delete cluster --name specdrift
# removes the 3 node containers, Argo CD, everything.
# your kind-microshop class cluster is untouched.
reclaim disk
docker image rm specdrift:0.1.0 specdrift:latest
docker system prune          # dangling build layers; asks first
docker builder prune         # the build cache, which gets large
Leaving it running is fine

The cluster costs you some RAM and nothing else. But it does not survive a reboot cleanly — after restarting your Mac, start Docker Desktop first, then the kind containers come back on their own. If they don't: docker start specdrift-control-plane specdrift-worker specdrift-worker2.
