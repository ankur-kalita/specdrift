Start here

The one-sentence version

We are building a small program that writes down what your laptop is made of, so that later it can tell you what changed — and then we are going to wrap it in an automated robot that checks our work every single time we save it.

The program is the fun part. The robot is the point. That robot is called CI, and by the end of this you will have built one from scratch and be able to explain every line of it.

The main idea

So what is CI, really?

CI stands for Continuous Integration. Ignore the name — it's a bad name and it explains nothing.

Here is what it actually is: a computer somewhere else that runs your tests every time you push code to GitHub. That's it. That's the whole concept.

Think of it like this

Imagine a very strict friend who lives in the cloud. Every time you save your homework, they grab a fresh copy, do it over from scratch on their own computer, and text you either ✅ or ❌.

They never get tired, they never say "it works on my machine", and they always start from zero — so they catch the stuff you forgot to save.

Why anyone bothers

Because "it works on my machine" is the single most expensive sentence in software. Your laptop has your files, your settings, your installed tools. The cloud computer has none of that. If your code works there, it genuinely works.

Everything else you'll hear about CI — jobs, matrices, artifacts, caching — is just detail hanging off that one idea.

The program

What specdrift does

Two commands. The first takes a photo of your machine. The second compares today's machine against that photo.

zsh — specdrift
$ specdrift snapshot -o baseline.json
saved 14 facts to baseline.json

... a week passes. macOS updates. you plug in a USB drive ...

$ specdrift diff baseline.json
  ~ os.version          15.6 -> 15.7
  + disk./Volumes/USB   62.9 GB
2 changes (exit 1)

That's genuinely useful on its own — "my machine feels slower, did something change?" is a real question with no easy answer today.

The clever bit: exit codes

When any program finishes, it hands back a single number. 0 means "fine". Anything else means "not fine". Every CI system on earth reads that number and nothing else.

NumberWhat it means
0Nothing changed — the pipeline goes green
1Something drifted — the pipeline goes red
2Something broke (missing file, bad JSON)

Because we chose those numbers deliberately, specdrift can be dropped straight into a pipeline as a check. You'll feel how CI and programs talk to each other, instead of being told about it.

One design decision worth understanding

Some facts about your laptop never change — the CPU model, the total RAM. Others change every second — how much memory is free right now.

If we compared everything, the answer would always be "everything changed!" and the tool would be useless. So each fact is labelled stable or volatile, and we only compare the stable ones unless you ask for --all.

That's a small thing, but it's the difference between a tool and a toy.

The code

How the program is split up

Four small files. The split between them is the one thing I'd love you to take away from this project, because it's why the CI part will work at all.

Pure · testable anywhere

facts.rs

Describes what a "fact" is and turns the whole snapshot into JSON text and back.

Pure · testable anywhere

diff.rs

Takes two snapshots, hands back a list of what's different. Never touches your actual hardware.

Touches the real machine

collect.rs

The only file that asks your laptop questions. Deliberately kept boring — it just fills in a list.

Touches the real world

main.rs

Reads your command, prints the output, picks the exit code.

Why the split matters (this is the good part)

Our CI robot runs on a Linux machine in a data centre. It is not a MacBook. It has different chips, different memory, different disks.

So imagine we'd written a test that says "check the CPU is an Apple M4". On your desk: passes. In the cloud: fails instantly, forever, and you'd have no idea why.

Because diff.rs never asks the real machine anything — you hand it two made-up snapshots and it just compares them — it gives the same answer on any computer on Earth. That's what makes it testable in CI.

The lesson underneath

Code that is easy to test and code that works in CI are the same code. People usually learn this the painful way, after a week of red pipelines. You're getting it up front.

The pipeline

The robot we're building

A "pipeline" is just a text file telling GitHub what to run. A job is one chunk of that work. Jobs can run side by side, or wait for each other.

Ours has three jobs, arranged like this:

Here's roughly what that looks like as a file. Don't worry about understanding it yet — we'll write it together, line by line, and I'll explain each piece as we add it.

.github / workflows / ci.yml
on: [push, pull_request]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - run: cargo fmt --check
      - run: cargo clippy -- -D warnings

  test:
    runs-on: ubuntu-latest
    steps:
      - run: cargo test

  build:
    needs: [lint, test]        # <- wait for both
    strategy:
      matrix:
        os: [ubuntu-latest, macos-latest, windows-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - run: cargo build --release

The plan

How we'll actually do this

We push to GitHub at every step, so you watch the pipeline grow instead of it appearing finished and mysterious.

  1. Empty project on GitHub

    Create the repo, make an empty Rust project, push it. No robot yet — on purpose.

    you'll see your repo, live, with nothing checking it

  2. The smallest possible robot

    One file, one job, three steps. We'll read it together until every line makes sense.

    you'll see your first green checkmark ✅

  3. Write the real logic, tests first

    Build facts.rs and diff.rs by writing the test before the code. Sounds backwards. Works beautifully.

    you'll see your tests running on a computer in a data centre

  4. Break it on purpose

    We'll deliberately push broken code and read the red failure log together. Reading a failed pipeline is the actual skill — one that only ever goes green teaches you nothing.

    you'll see a red ❌, and learn to not panic at it

  5. Make it a real program

    Add collect.rs and main.rs. Now it reads your actual laptop and you can run it for real.

    you'll see specdrift working on your own machine

  6. Split into three jobs + the matrix

    Turn the one small job into the fan-out shape from the diagram above, and add caching.

    you'll see the job graph branch out, and get much faster

  7. Ship version 0.1.0

    Add the release file, tag the version, push the tag.

    you'll see real downloadable programs on a real release page
Reference

Every word I used that I shouldn't have assumed

Open any of these whenever you hit the word and it doesn't mean anything to you. There's no order — dip in.

repo / repository

A project folder that Git is tracking. When it lives on GitHub, other people (and robots) can reach it. "Push to the repo" = "send my saved work up to GitHub".

commit

A save point, with a note attached explaining what you changed. Your project's history is a chain of these. Committing is local — it doesn't leave your laptop until you push.

push

Uploading your commits to GitHub. This is the moment the CI robot wakes up.

pipeline / workflow

Two words for the same thing: the file that tells CI what to do. GitHub calls it a workflow; most of the industry says pipeline. They live in a folder called .github/workflows/.

job

One chunk of work inside a pipeline, running on its own fresh computer. Our pipeline has three: lint, test, build. Separate jobs get separate machines — which is why they can run at the same time.

runner

The actual computer GitHub rents you to run a job. It's created from scratch, runs your steps, and is destroyed. Nothing survives between jobs unless you explicitly save it.

matrix

A way to say "run this same job several times with one thing changed". We use it to run one build definition on Linux, macOS and Windows without writing it three times.

artifact

A file the robot made that you want to keep — here, the compiled program. Because the runner is destroyed afterwards, anything you don't explicitly save as an artifact is gone.

caching

The runner starts empty every time, so it re-downloads all of Rust's building blocks on every run — about 3 minutes wasted. A cache stashes them between runs and cuts it to roughly 30 seconds. You will see this difference with your own eyes.

tag

A permanent name stuck onto one specific commit, usually a version number like v0.1.0. We use a tag as the signal that means "this one is worth publishing".

exit code

The single number a program hands back when it finishes. 0 = fine, anything else = not fine. This is the entire language CI speaks. Green checkmark = your steps all returned 0.

YAML

The file format pipelines are written in (files ending .yml). It's just lists and labels — but indentation is meaningful, so a stray space genuinely breaks it. This trips up absolutely everyone, including people who've done it for years.

cargo

Rust's do-everything tool. cargo build compiles, cargo test runs tests, cargo fmt tidies formatting. Roughly what Maven is in your Java class.

clippy

Rust's built-in advisor. It reads your code and points out things that work but could be better. Making CI treat its advice as errors is a cheap way to keep quality from sliding.

linting

Automated nitpicking — checking style and suspicious patterns rather than whether the code works. It's the cheapest, fastest check, which is why it runs first.

pure function

A function where the same input always gives the same output, and which doesn't reach out to the world — no reading files, no asking the hardware. Pure functions are trivial to test, which is exactly why we pushed all our real logic into diff.rs.

TDD (test-driven development)

Writing the test before the code. You describe what you want, watch it fail, then write just enough to make it pass. It feels backwards for about an hour and then feels obvious.

JSON

A plain-text way of writing structured data that both humans and programs can read. Our snapshots are JSON files — you can open one in any text editor and just read it.

One decision, in plain words

Should we also learn Docker here?

In your Java class, the pipeline ends by packing the app into a container — a sealed box holding the program plus everything it needs to run, so it behaves identically anywhere. Docker is the tool that makes those boxes.

I left that step out of your Rust project. Here's the honest trade-off:

My suggestion — leave it out

Learn one thing properly. Docker is a whole subject of its own. Bolting it on means you'd be learning CI and containers simultaneously, and probably half-learning both. We can add it in an afternoon later, once CI feels easy.

The case for putting it in

Two projects that mirror each other. Your Rust pipeline would have the same shape as your Java one, so each reinforces the other and the class material sticks harder. Costs about 20 extra lines.

Either answer is genuinely fine — just tell me "leave it out" or "put it in" and I'll start building.
